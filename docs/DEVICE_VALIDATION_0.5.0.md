## 已完成：本地 AI、真实 NPU 与故障回退

Debug APK 的本地 AI instrumentation 共七个用例：六个通过，一个因“GPU 必须是首选后端”的
假设不成立而预期跳过。当前首选是已经可用的 NPU；该跳过不是 GPU→CPU 故障用例在本版通过的证据。

| 验证 | 真实结果 |
| --- | --- |
| Hexagon NPU worker | 原有 GGUF 实际生成 13 tokens，服务日志耗时 4,006 ms |
| 严格 CPU worker | 实际生成 13 tokens，6,354 ms；CPU 路径不加载 GPU 核心 |
| NPU 进程故障回退 | 流式收到八段输出后主动结束 NPU worker，同一请求切换独立 GPU worker，生成 128 tokens，GPU 服务日志耗时 23,098 ms |
| Binder/Looper 请求关联 | CPU、GPU 各 20 个无效模型请求仍正确返回对应 request id，不因 Message 回收丢失请求 |
| 服务退出与隔离 | worker 退出不直接终止界面进程，失败通过 IPC 回到调用端 |

上述耗时来自具体短任务和服务日志，包含各任务不同的加载/初始化成本，不是公平的 NPU/GPU/CPU
吞吐比较，也不是长作文、热稳定性或准确率保证。故障回退会重新在下一后端生成，不承诺保留先前半句输出。

NPU 不是型号识别或改名：使用 ggml-org 官方 b11982 Snapdragon 运行库，HTP v79/CDSP 会话、
HTP0 矩阵算子和 37/37 层卸载已经在独立 CLI 留证；之后 APK 中的独立 NPU worker 也实际成功返回文本。
CPU 仍参与分词、采样和辅助计算，因此称为 NPU 加速，而不是“全部计算只用 NPU”。
运行库来源、SHA-256、进程 ABI 隔离和详细硬件证据见 [Hexagon 说明](NPU_HEXAGON_0.4.4.md)。

GPU 的实际路径为设备公开的 Adreno OpenCL 驱动，不是此前在 Q4_K decode 上失败的 Vulkan 路径。
NPU 的 b11982 核心和 GPU/CPU 的 b10333 核心不在同一个进程混装，也不打包手机厂商系统驱动。

### “立即回退”的准确边界

检测到初始化/推理错误、Binder 死亡或子进程退出后，会立即进入失败路由并尝试 GPU/CPU；
不需要等待完整的生成超时。这不等于下一后端立刻完成输出，启动、模型加载和重新生成仍需时间。

另一个不同场景是 native/驱动仍存活，但没有返回 IPC 或新输出的静默卡死。当前生成等待上限为
**12 分钟**，连接超时为 15 秒；尚没有更短的“无进展心跳”看门狗。不能把已验收的死亡检测回退
描述成任何未知卡死都能瞬间切换。该限制需要在后续长任务和驱动压力测试中继续评估。

## 已完成：离线语音修复与回归

首次组合测试确实出现过一次英国音色失败：十个 AI/语音用例中一个语音用例失败；这次失败没有隐瞒或
算作通过。定位到 sherpa-onnx 1.13.2 的 piper/eSpeak 前端调用 `espeak_SetVoiceByName`，
错误使用语言别名 `en-gb` 可触发 native abort。现已使用规范 voice 名：英国 `en`、美国 `en-us`。

修复后，`NaturalVoiceProcessIpcTest` **五个用例全部通过**，耗时 102.302 秒，覆盖：

- 默认单词、英国音色与所选慢速、跨页面全局偏好。
- 全部八种 Kokoro 音色实际合成/播放，而不只是模型初始化。
- 长段落合成/播放；返回实际播放状态、24 kHz PCM 和有效非空样本。

正常发音统一使用本地 Kokoro-82M v1.0 int8，词汇、精听、口语页面不再绕过它直接调用系统机器音。
合成和播放留在独立语音进程，包含 NaN/无穷、静音、严重削波检查、重复短音频缓存和延迟初始化。
语音自然程度仍有主观差异；这些结果证明有效离线生成与播放，不等于母语真人录音或用户偏好的保证。
模型来源、英美音色、许可证及修复版 int8 SHA-256 见 [离线语音说明](OFFLINE_VOICE.md)。

最终非调试 performance APK 的设置页也实际试听成功：`af_heart`、1.0×，
24,000 Hz、113,503 个样本，语音日志耗时 7,199 ms（11:50:14），没有进入错误/系统 TTS 回退流程。
暗色界面已截图目视检查；检查后恢复原亮色设置及 1.0× 字体比例。

## 已完成：滚动性能

已经实施后台加载/搜索、稳定列表 key、预排序及进度通知限频；performance APK 关闭调试并启用 R8。
App 只修改自己窗口的刷新率偏好，不改手机全局刷新率设置。真机已观察到新窗口实际 120 Hz；
系统仍可因省电、温控或厂商策略拒绝该偏好。

旧版 0.4.3 的可重复基线为 60 Hz、二十次 250 ms 词本滑动：873 帧、21 个 janky frames（2.41%），
帧工作耗时 P50 5 ms / P95 15 ms / P99 32 ms。它不是 120 Hz 基线，也不是触摸到显示的延迟测量。
最终非调试 performance APK 在相同二十次滑动脚本下，实际 **120 Hz、1,693 帧、现代 jank 0**，
帧工作耗时 P50/P90/P95/P99 为 **5/5/5/6 ms**，Slow UI thread 和 deadline missed 均为零。
Legacy jank 仍有一个（0.06%）；系统 High input latency 原始计数为 1,056，未下降，
不能因为现代 jank 为零就宣称所有输入延迟已经解决。

两轮同时改变了布局、数据处理、调试/非调试构建和 60→120 Hz 策略，不是单一修改的严格 A/B；
帧耗时和系统计数也不是手指触摸到屏幕呈现的端到端延迟。完整方法、原始计数和边界见
[滑动验收报告](PERFORMANCE_0.5.0.md)。
